# Архитектурные решения Ships RPG

## SR-ADR-001 — стабильные ID и постепенное включение (2026-11-09, принято)
Контекст: runtime содержит 12 моделей и локализованные классы; новый контракт требует 15 моделей, 12 классов, 30 специализаций.
Варианты: сразу заменить runtime; расширить данные через проверяемый реестр.
Выбор: `shipcatalog/data/rpg_identity.json` хранит новые стабильные идентичности; schema и Go-валидация проверяют полноту/ссылки. 15 моделей относятся к 12 классам: оба истребителя — fighter, корветы — corvette, фрегаты — frigate. Текущие 12 ID сохраняются. Специализация получает глобальный ID `SHIP-ID:local_id`, а старые локальные ключи сохраняются до отдельной миграции.
Последствия: реестр ещё не игровые паспорта и не runtime-функциональность; не меняет баланс, starters, активные версии PostgreSQL или сохранения. Подключение — отдельная задача. Имена новых local_id — проектное предложение, не изменение старых ключей.

## SR-ADR-002 — конфликты прежних решений (2026-11-09, согласовано владельцем)
Контекст: АР-4 60/30 против 100/50; АР-2 10–15 узлов против 6. Основная карта запрещает самостоятельно разрешать конфликты.
Варианты: подтверждённая замена; сохранение старого поведения.
Выбор: вопрос владельцу отправлен, зависимые задачи BLOCKED до ответа. Остальные задачи разрешены текущим запросом. Мастерство классов и общее дерево пилота сохраняются.
Последствия: caps и специализационные деревья runtime пока не изменять. Текущий запрет production-деплоя имеет приоритет над историческим постоянным разрешением.

Результат: владелец ответил «Да, применить новые требования». Лимиты 100/50 и дерево 6 + усиление 20 утверждены, блокировка снята. SR-014a меняет только MaxLevel, сохраняет Base/Growth и накопленный XP; возможен рост уровня у игрока с запасом XP выше прежнего cap — ожидаемое поведение. Реальных данных/БД не переписывать, сначала проверять синтетическими тестами. Полные деревья специализаций — SR-014 после каталогов умений.

## SR-ADR-003 — полные паспорта без публикации runtime (2026-11-09, принято)
Контекст: ShipSpec/Ship_Patch_Pack_v1 используются действующей игрой, версиями БД и админкой; SR-011 должен добавить поля, не меняя старые числа.
Варианты: расширить runtime и сразу включить новые корабли; создать полный проверяемый документ v2 и отдельно интегрировать позднее.
Выбор: `PassportCatalog` содержит 15 полных паспортов; `base` — полный снимок ShipSpec, а новые поля — отдельные типизированные данные. Проверка `CheckLegacyPassportBases` сравнивает все 12 старых ShipSpec со встроенным seed, включая карты способностей; публикация в существующий Service/Store в SR-011 не выполняется. Активные админские значения не перезаписываются. При будущей интеграции брать активный снимок через Service.Active, сохранять его правки и отдельно мигрировать новые поля/локальные специализации.
Последствия: новый каталог пока не виден в клиенте. Дублирование seed-значений в snapshot обнаруживается тестом совместимости. `base.specs` сохраняет старые локальные ключи, `specializations` — ровно два новых глобальных ID; они не подменяют друг друга до явной миграции.

Единицы: dimensions_m = [длина, ширина, высота] в метрах; визуал Godot: -Z вперёд, +Y вверх, позиции креплений [X,Y,Z] в метрах. Скорость/ускорение/дальности задаются в существующих единицах мира: их нельзя автоматически пересчитывать из метров. Масса сухого корпуса отдельно от бюджета массы оборудования; MW размещения отдельно от боевого energy. Новые resistance-коэффициенты не применяются поверх старой armor до интеграции расчёта.

Стартовые модули — самодостаточные предложенные blueprints с семейством, категорией, размером, массой, мощностью, слотом и ID разрешённых навыков. Family не является ссылкой на ещё не созданный справочник. В SR-013 вынести их в общий каталог и проверить все unlock-пути; текущие проверки не заменяют транзакции владения/уникальности SR-030. `allowed_abilities` ссылается на 72 ID утверждённого ТЗ; schema проверяет точный диапазон ID, но не существование реализаций эффектов (SR-012/020).

Каждый новый блок полей помечен `preliminary_fields`; у трёх новых моделей предварителен и весь base. UI-заглушки, экономика и NPC — контракты предложений, а не уже исполняемая механика.

## SR-ADR-004 — сквозная интеграция и общая main (2026-11-09, подтверждено владельцем)
Контекст: наполнение всех 72/30/36 до первого игрового использования откладывает проверку интерфейса/сохранений.
Варианты: завершить все каталоги; подключать законченные сквозные шаги.
Выбор: сначала Стриж, начиная с серверного паспорта в ангаре, затем стартовый ENG/M01, серверная доступность, док/бой/сохранение, HUD и игровой прогон. Затем расширять. Требования SR-012…070 сохраняются, но не являются полным барьером первого подключения. Пользователь явно разрешил публикацию работы/прогресса в main и APK при необходимости через существующий механизм Claude.
Последствия: публиковать проверенные изменения без force с актуальными статусами main/CI/test/prod/APK. Production-деплой по-прежнему требует отдельного разрешения; создание APK и публикация обновления — разные действия. Существующие ключи подписи обязательны.

## SR-ADR-005 — первая совместимая игровая интеграция (2026-11-09, принято)
Контекст: надо проверить путь сервер → ангар до модулей/сохранений, не сбросить активные правки админки и не сломать старый APK.
Варианты: заменить world.Doc новым паспортом; новая обязательная команда; дополнить существующий ships response.
Выбор: optional passport + ship_max_level в ships, только для текущего Стрижа. Сервер накладывает текущий World.SpecInfo (с уровнем/админскими значениями) поверх metadata. main инициализирует проверенный каталог без SetCatalog, provider nil отключает расширение в тестах/альтернативных конфигурациях. Клиент передаёт секцию через прежний сигнал ships_updated, старые ответы скрывают/очищают её. Ангар показывает предварительный план оснащения отдельно от живых статов; не даёт модули/бонусы до SR-100b/c. Старый hardcoded cap30 заменён авторитетным cap сервера или отображением уровня без выдуманного максимума.
Последствия: смена APK нужна для новой секции; серверный путь совместим с прежним APK. Сквозная проверка — реальный ephemeral Go WS + Godot gateway + hangar без БД; tools/test_client.sh включает её в существующий Godot CI job. Это не production/Android приёмка.
