# NAV-WORLD: Техническое задание — живая расширяемая галактика

Версия: 1.0 (Kimi Code, 2026-11-10). Статус: **ТЗ, реализация запрещена без отдельного разрешения владельца**.
Основание: NAV-BORDER-001 (границы и гиперпереходы), NAV-WORLD-002 (расширяемые системы), NAV-WORLD-003 (эволюционирующий мир, утверждён вариант C).
Метод: расширение существующей архитектуры. Ни одна работающая механика не удаляется; новые системы появляются как модули внутри существующего Go-сервера.

## 1. Краткая архитектурная концепция

Галактика «Звёздных рубежей» строится как **трёхуровневая модель**:

1. **Галактика** — граф систем (узлы) и гиперкоридоров (рёбра), общие правила владения, экономика и история. Уже существует в зачатке: `world.Router` (3 системы, `internal/world/router.go`), реестр 40 систем — `docs/design/GALAXY_R30.md`.
2. **Система** — насыщенное ядро + внешние сектора 2048×2048 GU с состояниями ACTIVE/WARM/DORMANT. Сегодня система — единый мир `world.World` с радиусом 1400; секторной модели нет.
3. **События и история** — единая журнально-очередная шина (`world_events`), от которой питаются экономика, ИИ-цивилизация, история галактики и динамические события. Частично существует: `Reward`/`Event` в мире, `xp_grants`-паттерн идемпотентности.

Ключевые принципы:

- **Сервер — единственный источник истины** (движение, переходы, добыча, экономика, влияние). Клиент показывает и предлагает.
- **Идемпотентность всего, что начисляет или перемещает**: паттерн `UNIQUE (player_id, grant_key)` и ключа запроса уже повсеместен (`reward_grants`, `xp_grants`, `shop_purchases`, `shipxp`) — распространяется на все новые операции.
- **Детерминизм генерации**: seed + версия генератора в каждом идентификаторе сектора; география не меняется «под игроком».
- **Расширение, а не замена**: Router расширяется до SectorRouter, worldgen получает версии, aiagent — цели, появляются пакеты `border`, `sector`, `galhist`, `dynel` (динамические события) — все внутри одного бинаря (VPS: 4 vCPU/8 ГБ, микросервисы преждевременны).

## 4. Спецификация NAV-BORDER-001: границы и гиперпереходы

### 4.1. Навигационные узлы (Gate → Node)
Существующие `Gate` (`router.go`) эволюционируют в **NavNode**:

```go
type NavNode struct {
    ID         string   `json:"id"`          // "aurora:gn-1"
    System     string   `json:"system"`
    Pos        [2]float64 `json:"pos"`
    Kind       string   `json:"kind"`        // gate | rift(временный) | survey(исследовательский)
    Links      []Link   `json:"links"`
    Requires   Req      `json:"requires"`    // fuel_range, scanner_level, faction_standing, discovery
    PvPBlock   bool     `json:"pvp_block"`   // блокировка узла при флаге боя
}
type Link struct {
    ToNode  string `json:"to_node"`   // узел в другой системе
    Hidden  bool   `json:"hidden"`    // известен только открывшим
    Faction string `json:"faction"`   // контролирующая сторона (влияние NAV-WORLD-003)
    Fuel    int    `json:"fuel"`      // базовый расход топлива
}
```

- Узлы видны на звёздной карте; **скрытые коридоры** (`hidden: true`) не отображаются, пока не открыты записью в `player_discoveries` (таблица открытий, §6).
- Гиперпереход **невозможен вне узла**: серверная проверка остаётся как сейчас (расстояние до узла ≤ радиуса действия), плюс новые проверки — поэтому «бегство от PvP прыжком из любой точки» невозможно конструктивно.
- **PvP-блокировка**: при активном боевом флаге игрока (последний урон/агрессия < 30 с, по правилам АР-1) узел отказывает с кодом `pvp_locked`. Переход не спасает от боя; бежать надо к узлу до начала боя или выигрывать дистанцию обычным полётом.
- **Групповые переходы**: для пати (существующие эскадры `world/fleet.go` + живые игроки в группе) переход лидера инициирует приглашение; каждый член подтверждает своим `jump`; сервер атомарно переносит подтвердивших в целевую систему одной транзакцией с ключом `groupjump:{leader}:{node}:{minute}` (идемпотентность, защита от дублей).
- **Разрыв соединения**: внутри прыжка (между `jump` и `system_changed`) соединение может оборваться — текущая модель «корабль остаётся в мире 10 с, позиция сохраняется» расширяется: недоприменённый прыжок откатывается (игрок остаётся в исходной системе, ключ переода не записан), полностью применённый — персистентен (миграция `players.current_system` уже атомарна). Тест №10.
- **ИИ-переходы**: `aiciv.goals.Galaxy` уже переносит капитанов; добавляется проверка тех же ограничений (узел, топливо ИИ-экономики) и запись в общий журнал маршрутов.

### 4.2. Гипердвигатель и топливо
Новый ресурс корабля `fuel` (паспорт корабля, `shipcatalog`): ёмкость по классу, расход = `link.Fuel * (1 + масса груза/трюм) * коэфф. регион`. Дозаправка у станции за кредиты; предел «дальности прыжка» = можно совершить N прыжков без дозаправки, что ограничивает проникновение в дальние системы без логистики. Топливо — серверное число, клиент лишь показывает.

### 4.3. Маршруты
Серверный построитель маршрутов по графу `NavNode` (Дейкстра по `fuel`, альтернативы: быстрый/безопасный/дешёвый — веса из влияния фракций, опасности зон и цен). Клиент: в звёздной карте тап по дальней системе строит маршрут цепочкой; автопилот исполняет его как очередь `jump` с долетом до узлов (отмена — любое ручное управление, как сейчас для автопилота).

### 4.4. Протокол (аддитивно, версия протокола прежняя)
- `jump {to, node?}` — добавляется `node` (конкретный узел при нескольких).
- Ошибки: `pvp_locked`, `no_fuel`, `not_discovered`, `node_closed` (временный узел), прежние `no_link/no_gate/no_system`.
- `welcome/system_changed` дополняются `fuel` в `ship` и `nodes` текущей системы (вместо/рядом с `gates`).

## 5. Спецификация NAV-WORLD-002: расширяемые системы

### 5.1. Зонирование системы
Каждая система делится на **ядро** (существующий круг: станция, стартовые зоны, сюжетные объекты — без изменений радиуса) и **кольцо секторов**: сетка 2048×2048 GU за пределами ядра, адрес сектора `(system, qx, qy)` (quad-ключ). Тип системы (`core|normal|industrial|dangerous`) задаёт радиус насыщенной зоны (8000/12000/16000/20000 GU) — параметр `SystemParams.SaturatedRadius`, не константа в коде.

### 5.2. Состояния секторов
- **DORMANT** (по умолчанию): объектов в памяти нет; при обращении генератор отдаёт географию по seed; агрегаты (запасы, состояние влияния) — в БД.
- **WARM**: играющие рядом (соседний сектор с игроками) → лёгкая симуляция: дрейф NPC-агрегатов, тики экономики сектора, подготовка декора.
- **ACTIVE**: есть игроки → полная симуляция как сейчас: NPC, месторождения с живым `Amount`, бой.
- Переходы не обнуляют состояние: `Amount` месторождения — в БД (`sector_resources`), при активации поднимается в память; при усыплении — сброс обратно. Бой не «исчезает»: уход всех игроков из ACTIVE-сектора переводит бой в агрегат (NPC возвращаются домой, урон сохраняется в снапшотах сектора).

### 5.3. Пространственный индекс и AOI
- Сервер: uniform grid по секторам; объекты мира хранятся по `sector_key`; снапшот игроку собирается из его сектора + соседей (8) с фильтром по радиусу (существующий подход фильтра ИИ-1 обобщается).
- Сетевой трафик: полные апдейты — только ACTIVE-рядом; изменения агрегатов — через очередь событий.
- Бюджет: сектор ACTIVE стоит не дороже текущего «мира системы» (он и есть эталон нагрузки).

### 5.4. Процедурная генерация секторов
`worldgen` расширяется до версионированного `SectorGen v1`:
- Вход: `seed_system` (есть), `sector_coord`, `gen_version` (новое поле; смена версии меняет только новые/недостроенные зоны, существующая география мира игроков защищена флагом `pinned` у занятых секторов).
- Выход: те же примитивы, что сейчас (`zones/deposits/bodies/...`) + новые: газовые облака (непроходимые для мининга обычным модулем), секретные объекты (тайники высокого ранга), пиратские базы (точки спавна рейдеров, связь с NAV-WORLD-003 влиянием).
- Сюжетные объекты (глава 1, станции ядра) — в `pinned`-ядре, генератор их не трогает.
- Сохранение открытий: `player_discoveries(player_id, system, sector, kind, ref, first_at)` — idempotent; первое открытие сектора/объекта кормит историю (§6.6) и журнал `location`.

## 6. Спецификация NAV-WORLD-003: эволюционирующий мир (вариант C)

### 6.1. Общая шина событий
Новый пакет `galhist` + таблица `world_events`:

```sql
CREATE TABLE world_events (
  id BIGSERIAL PRIMARY KEY,
  at TIMESTAMPTZ NOT NULL DEFAULT now(),
  system TEXT, sector TEXT,
  kind TEXT NOT NULL,        -- discovery|build|destroy|capture|war|economy|corridor|anomaly
  actor TEXT,                -- player:<id> | ai:<captain> | corp:<id> | faction:<id> | server
  payload JSONB NOT NULL,
  key TEXT UNIQUE            -- идемпотентность: 'mineout:<deposit_id>' и т.п.
);
```

Правило: **история пишется только подтверждёнными серверными фактами** (после транзакции, не до). Подписчики: история галактики, динамические события, экономика, ИИ-цели, карта (бейджи «новое»).

### 6.2. Инфраструктура (строительство)
- Таблицы `structures(id, system, sector, owner_corp, type, level, hp, state, upkeep_due)` + `structure_jobs` (очереди строительства/ремонта с серверными таймерами — единый планировщик фоновых задач).
- Стоимость: кредиты + ресурсы из складов корпорации (существующий `corp` + `treasury`), сроки — часы/дни реального времени, обслуживание — периодический список с казны (просрочка → деградация уровня, не мгновенное исчезновение).
- Не разрушаемы: сюжетные станции ядра, станции фракций-столиц (`GALAXY_R30.md` §2.1 помечает столицы) — отдельное правило `protected` в типе структуры.
- Захват: только вне ядра и только после объявления войны (вариант АР-1), с подготовкой и решающей операцией; HP-объекты ремонтируемы.

### 6.3. Ресурсы: истощение и восстановление
- Месторождение получает глобальный запас: `sector_resources(deposit_id, amount_max_world, depleted_at)`. Локальный `Amount` (трюм-кубы месторождения) — как сейчас; когда сектор усыпляется, локальный остаток пишется в глобальный.
- Истощение → событие `mineout` → **не респаунится автоматически**; восстановление по типу: `iron_ore` — медленная регенерация доли (существующая логика, но с потолком), `crystals/gas` — частично через аномалии, редкие — только новые залежи через исследования/события.
- Антифарм: регенерация зависит от **игрового времени**, а не перезагрузки сектора; DORMANT не восстанавливает сверх лимита.

### 6.4. Влияние и территории
Таблица `influence(system, sector_quad, holder_type, holder_id, value, updated_at)`:
- Источники: торговля (объём проводок через структуры), патрулирование (убитые NPC пиратов в квадре), задания фракций, строительство, PvP-победы (по правилам АР-1).
- Модель: value в [-100..+100] на держателя; контроль квадрада — держатель с value ≥ 60 при отрыве ≥ 20 от второго. Скорость: тики раз в час, изменение ≤ 5/тик от одного источника (защита от накрутки), затухание −1/тик без активности.
- Преимущества: налог со структур (классическая ставка в казну держателя), скидка обслуживания, видимость событий квадра.
- Ограничения доминирования: мягкий потолок — чем больше квадров у держателя, тем дороже удержание; «захват галактики» экономически невыгоден; фракции-столицы не захватываемы.
- Антификтив: действия считаются только при экономическом смысле (проводки ≥ минимума, реальные тиковые потери NPC), шаблонные «пробеги» не дают влияния.

### 6.5. ИИ-цивилизация (на базе aiciv)
- Расширить `aiciv.goals`: добавить `Trade`, `Build`, `Defend`, `Expand` — каждая цель опирается на реальные ресурсы: ИИ-покупки = те же `SpendCredits`, добыча = те же месторождения (записываются в общий баланс, ИИ не создаёт ресурсы из ничего — контроль через ту же таблицу `sector_resources` и бюджеты).
- Фон: DORMANT-секторы с присутствием ИИ симулируются агрегатно — раз в N минут тик `aiciv` пересчитывает позиции/запасы по формулам (не пошаговая симуляция); при входе игрока капитан материализуется из сохранённого состояния (`spawnFromAggregate`) рядом с его логической позицией.
- Ограничения: бюджеты ИИ (кредиты/ресурсы в неделю) задаются сервером, антифарм — ИИ-капитаны не дают лут выше таблиц.

### 6.6. Динамические события и история
- Движок `dynel`: правила вида `WHEN <условие мира> THEN <событие> WITH <бюджет>` из таблицы `event_rules` (версионирована, редактируется данными). Семена причинности из §4.5 промпта: истощение → дефицит → рост цен → привлечение торговцев → пираты → спрос на охрану → восстановление безопасности.
- Ограничения: одновременно активных событий в системе ≤ 3; кулдаун на тип ≥ 6 ч; награды из бюджета события (не из ниоткуда).
- История: `world_events` — единственный источник для хроники; UI карты показывает маркеры последних N событий по фильтрам; «хроника» в клиенте — читаемая лента, сгенерированная из фактов (шаблоны подстановки из payload, без выдумок).

### 6.7. Экономика: источники и стоки
Еженедельный тик `economy tick` (фоновый, бюджетированный):
- Источники: добыча (≤ глобальных запасов), производство (по рецептам будущего крафта), лут PvE (таблицы), страховые выплаты (сток!).
- Стоки: потребление станций (upkeep), крафт, потери кораблей (уничтожение = списание), топливо, налоги (перераспределение, не сток).
- Контроль инфляции: мониторинг «кредитов в обращение» (сумма players.credits) и цен; при росте > порога за неделю — автоматические стоки (дороже ремонт/топливо/страховые). Пороги — конфиг, не код.
- Всё журналируется в `world_events(kind='economy')`.

## 7. Структуры данных и API (сводно)

Новые таблицы: `nav_nodes`, `nav_links`, `player_discoveries`, `sector_states`, `sector_resources`, `structures`, `structure_jobs`, `influence`, `world_events`, `event_rules`, `ai_civ_state` (агрегаты), `fuel` — поле в паспорте/состоянии корабля (миграции строго расширяющие, как принято).

Новые WS-сообщения (аддитивно, все в список известных типов): `nav_route {to}` → `nav_route {steps[]}`; `jump` дополняется `node`; `sector_state` (подписка клиента на агрегаты соседних секторов); события приходят через существующий `events`-канал. Все начисления/переходы/строительство — с ключами идемпотентности.

## 8. Серверные алгоритмы (ключевые)

1. **SectorRouter**: заменяет прямую маршрутизацию Router по мере готовности; Router остаётся для ядра систем (совместимость).
2. **Активация сектора**: `ensureSector(system, quad)` — подъём из `sector_states` + `sector_resources`, генерация geography по seed, спавн NPC из агрегатов; бюджет: не более K активных секторов (K из конфига, старт 4).
3. **Тикер мира**: один планировщик (заменяет разрозненные горутины): очередь с приоритетами — бой (20 Гц, ACTIVE), экономика (1/час, все сектора), влияние (1/час), события (по правилам), ИИ-агрегаты (1/10 мин).
4. **Гиперпереход**: расширение текущего `Router.Jump` — проверки: узел (расстояние), `pvp_locked`, топливо, открытие коридора; списание топлива и ключ `jump:{player}:{node}:{day}` в одной транзакции с переносом записи.
5. **Серверные бюджеты**: на каждый тик измеряется время; при превышении бюджета тикера — деградация (WARM-окно расширяется, NPC-кап срабатывает раньше). Метрики: Prometheus-эндпоинт `/metrics` (без внешних зависимостей — счётчики в памяти + текстовый формат).

## 9. Процедурная генерация (итог требований)

Детерминизм: `gen = sha1(seed_system | gen_version | quad)`; версия в конфигурации мира (версионирование как у `worldcfg`); `pinned`-ядра; тест на стабильность географии при бампе версии (сценарий №14). Типы контента — перечислены в §5.4; редкость секретных объектов — табличная, зависит от типа системы и глубины (дальше от ядра — выше шанс редкого).

## 10. Экономические формулы (стартовые, конфигурируемые)

- Расход топлива прыжка: `F = base_link * (1 + 0.5 * cargo_fill) * danger_coef`.
- Upkeep структуры: `U = base_type * 1.15^level` кр/сутки.
- Влияние за тик: `Δ = clamp(source_gain, -5, +5)`, затухание `-1` без активности.
- Регенерация месторождения: `iron_ore`: +0.5%/час до 40% от max; `crystals`: +0.1%/час до 25%; редкие: 0 (только новые залежи).
- Антиинфляция: при `ΔM/M > 15%/нед` → коэффициент стоков ×1.2 до следующего тика.

## 11. Механики ИИ (итог)

Цели из `aiciv.goals` + экономические проводки через общие сервисы; агрегатная симуляция DORMANT; материализация при появлении игрока; бюджеты и антифарм. ИИ не обязан быть «честнее игрока» по скорости, но обязан по правилам: те же таблицы лута, те же запасы, те же проверки.

## 12. Интеграция с картой и HUD

- Звёздная карта (`star_map_screen.gd`): слой узлов (иконки видов), скрытые коридоры — пунктир после открытия; слой влияния (заливка квадров держателями); слой событий (маркеры с фильтром); слой истории (по тапу — лента фактов).
- Карта системы (`map_screen.gd`): масштаб «сектор» — сетка квадров, туман войны по `player_discoveries`, опасность по событиям.
- HUD: топливо рядом со статус-чипом; новые элементы — через существующий редактор раскладки (перемещение/прозрачность/сброс), механизм настроек `UiSettings` — единый для всех новых элементов (отдельный фреймворк не создаётся).
- Адаптивность: все новые экраны проходят `layout_test` сценарии (6 размеров + вырезы).

## 13. Совместимость с другими системами

| Система | Интеграция |
|---|---|
| Кампания/квесты | Ядро систем pinned; цепочки главы 1 не меняются; новые квесты — через `quest.Service.Event` от `world_events` |
| PvE/боссы | Логово босса — pinned-объект; секторные NPC — те же `npc`-типы |
| Пати/группы | Групповой прыжок через существующую пати; эскадры `fleet.go` |
| Корпорации | Структуры/войны/казна — расширение `corp` |
| Открытое PvP | АР-1: узлы не спасают от боя (`pvp_locked`); захват только через войну |
| Лут/обломки | Без изменений; события добавляют источники таблицами |
| Страхование | Будущий сток экономики (формулы готовы) |
| Прогрессия/Gear Score | Без изменений; сектора дают новые источники XP через те же ключи |
| Экипаж | Не конфликтует; позже подключается к кораблям ИИ |
| Рынок/производство/аукцион | События и влияние дают спрос/предложение; очереди крафта — в `structure_jobs` |
| ИИ-игроки | aiciv — потребитель `world_events` |
| Автопилот | Очередь маршрутов; отмена ручным вводом (существующее правило) |

### Конфликты, требующие решения (не разрешаю сам)
1. **Масштаб GU**: текущий радиус системы 1400 GU vs предлагаемые 8000–20000. Прыжки внутри системы на таких дистанциях меняют баланс скорости (14 ед/с → часы полёта). Требуется либо внутрисистемный «форсаж/варп», либо уменьшение масштаба. Предложение: ядро 1400 сохранить, сектора — с варп-линиями между секторами (узлы внутрисистемной навигации по аналогии с гиперузлами). **Вопрос владельцу: согласовать варп-линии.**
2. **Топливо**: новая обязательная механика. Если владелец не хочет топливо сейчас — первый релиз NAV-BORDER без топлива (ограничения только узлами), топливо отдельным включением. **Вопрос.**
3. **Разрушение чужих структур**: связано с включением PvP (сейчас выключен). Строительство в первой фазе — только в PvE-аспекте (восстановление, апгрейд), захват — после A6. **Вопрос согласования порядка.**

## 14. Безопасность и антиэксплойты

- Все проверки переходов/строительства/влияния — сервер; клиент лишь рисует.
- Идемпотентные ключи на каждую операцию (шаблон `reward_grants`).
- Влияние: минимальные значимые пороги, скорость-ограничитель, детект «пробегов» (одинаковые маршруты туда-обратно без экономического эффекта не считаются).
- Ресурсы: глобальные запасы + игровое время; DORMANT-реген с потолком.
- Дубли кораблей при переходах: уникальный ключ прыжка + атомарный перенос записи (текущая модель `removePlayer→Join` в одном мьютексе Router сохраняется).
- Частота событий и награды — бюджеты, не формулы «чем больше, тем лучше».

## 15. Нагрузочные требования

- Не заявлять максимальный онлайн до измерений. Эталон: текущий мир системы = 1 ACTIVE-сектор; цель — 4 ACTIVE-сектора на VPS 4 vCPU/8 ГБ без роста latency тика (>50 мс p95 на тик).
- Бюджеты: тик боя 20 Гц (ACTIVE), экономика/влияние 1/час суммарно ≤ 5% CPU, генерация ≤ 2 с на сектор, сетевой трафик на игрока — не выше текущего ×1.5.
- Метрики: `/metrics` (длительность тиков, активные сектора, события в очереди, размер экономики) + алерты по порогам (развёртывание мониторинга — отдельная задача, не блокирует).
- Деградация: при нехватке бюджета — расширение WARM-окна, снижение NPC-капа, отказ новых активаций (очередь), НИКАКОГО молчаливого обнуления мира.

## 16. Тестовые сценарии (15 из ТЗ + производительность/безопасность)

Принимаются 15 сценариев промпта как обязательные; каждый — Go-тест (интеграция с testdb) и где касается UI — Godot-тест. Дополнительно:
- P1: активация 100 DORMANT-секторов ≤ 2 с суммарно на генерацию (без полной симуляции).
- P2: 1000 параллельных `jump` с одним ключом → ровно один применён.
- P3: перезапуск в середине группового прыжка → ни один участник не задвоен, недоприменённые откачены.
- P4: экономический тик 52 недели с эмуляцией фарма — отсутствие экспоненциального роста кредитов/ресурсов (тест-громоздка, допускается агрегированная модель в тесте).
- P5: бамп версии генератора — география pinned-секторов бит-в-бит прежняя.

## 17. Поэтапный план реализации

**Фаза 0 — аудит и фиксация (1 заход).** Зафиксировать этот документ в реестре (`tasks.json`: NAV-*), инвентаризовать pinned-объекты главы 1, выставить бюджетные замеры текущего тика (базовая линия). Критерий: базовые метрики записаны. Риски: нет. Откат: не требуется.

**Фаза 1 — секторная модель (большая).** Таблицы `sector_states/sector_resources`; SectorRouter ядро+кольцо; пространственный индекс; состояния ACTIVE/WARM/DORMANT с честными переходами. Критерий: сценарии 1,2,3,11,12 тестами зелёны; тик не дороже базовой линии. Риск: регресс текущего мира — откат флагом `COSMOC_FEATURE_SECTORS`.

**Фаза 2 — расширение систем.** Радиусы по типам, сетка 2048, внутрисистемные варп-линии (после ответа владельца), топливо (после ответа). Критерий: полёт ядро→внешний сектор→обратно без загрузочных экранов, клиент тянет декор сектора. Откат: конфиг радиусов = 1400 (поведение как сейчас).

**Фаза 3 — процген и открытия.** Версии генератора, `player_discoveries`, журнал `location` → `world_events`, секретные объекты. Критерий: сценарии 8,14; повторная генерация идентична; pinned целы.

**Фаза 4 — NAV-BORDER-001.** NavNode/Link, скрытые коридоры, маршрутизатор, групповые переходы, `pvp_locked`, восстановление (сценарий 10). Критерий: сценарии 8,9,10 + P2/P3. Риск: конфликт с текущими gates — миграция данных узлов из `jumps`.

**Фаза 5 — экономическая эволюция.** Глобальные запасы, истощение, `world_events`, экономический тик, формулы §10. Критерий: сценарии 4,7,15 + P4.

**Фаза 6 — инфраструктура и территории.** `structures`, очереди, upkeep, влияние и квадры, антификтив. Критерий: сценарии 5,6; PvE-строительство работает без PvP. Захват — за флагом, после А6.

**Фаза 7 — автономные ИИ.** Экономические цели aiciv, агрегатная симуляция, материализация. Критерий: сценарий 13; ИИ-торговля проходит общими проводками.

**Фаза 8 — история, UI, оптимизация.** Хроника на карте, слои влияния/событий, `/metrics`, нагрузочный прогон на VPS. Критерий: все 15 сценариев + P1–P5 зелёны, лендинг и ROADMAP обновлены.

Каждая фаза — отдельные коммиты и включение за флагом `COSMOC_FEATURE_NAVWORLD` (поэтапные под-флаги), миграции только расширяющие, бэкап перед выкаткой.

## 18. Критерии приёмки (общие)

1. Все существующие тесты зелёные (Go, Godot, admin).
2. Сценарии §16 автоматизированы и проходят.
3. Прыжок невозможен вне узла; скрытый коридор невидим до открытия; боефлаг блокирует узел.
4. Истощённое месторождение не восстанавливается перезаходом/рестартом.
5. История показывает только события из `world_events`.
6. DORMANT-сектор не потребляет CPU существенно (метрики).
7. Ни одна работающая механика не удалена; все новые функции выключаемы флагом.

## 19. Архитектурные риски

1. Масштаб GU и баланс скорости (варп-линии) — без ответа владельца фаза 2 частично заблокирована.
2. Рост сложности Router при 40 системах — граф мал, риск низкий; риск средний при секторах без индекса (решается фазой 1).
3. Экономические эксплойты ИИ-ферм — mitigations §14, но требуют наблюдения на живых данных.
4. Миграции узлов из `jumps` — одноразовая, расширяющая, с бэкапом.
5. Клиентский декор на больших радиусах — чанки/pinning уже есть; риск средний, решается порогом детализации.
6. Параллельная работа других ИИ (оснащение, дизайн) — интеграция через tasks.json/AGENT_TASKS, конфликты по `ws/hub.go` вероятны; порядок — фаза 1 не трогает боёвку.

## Решения, требующие утверждения владельца

1. **Внутрисистемные варп-линии** между секторами (иначе полёты 8000+ GU при скорости 14 ед/с нереалистичны). Альтернатива: уменьшить масштаб GU.
2. **Топливо гипердвигателя** — включать в первом релизе NAV-BORDER или отдельным поздним шагом.
3. **Порядок PvP**: строительство/захват структур до включения PvP (A6) — только PvE-строительство и влияние; захват — после.
4. **NPC-кап и WARM-окно**: предлагаю кап 200 NPC на ACTIVE-сектор (как лимит ИИ R-42) и WARM радиусом 1 квадр — утвердить или скорректировать.
5. **Экономические пороги** (регенерация, инфляционный триггер 15%/нед, ставки upkeep) — стартовые значения §10 как дефолты до баланс-прохода.
6. **Название и вид узлов на карте** — «навигационные узлы» vs «гиперврата» (термин для UI и лора).

> Независимо от ответов, фазы 0–1 и 3 (аудит, секторная модель, процген-версии) не блокируются и могут стартовать сразу после разрешения на реализацию.
