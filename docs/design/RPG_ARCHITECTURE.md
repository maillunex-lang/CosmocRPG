### Глоссарий (чтобы не путать)

- **Профессия пилота** (RPG-03): Перехватчик, Разведчик, Торговец, Шахтёр — то, что игрок выбирает при создании персонажа (`players.pilot_spec`).
- **Класс корабля**: истребитель, корвет, фрегат, эсминец, крейсер (+ назначения: шахтёр, грузовой, разведчик, поддержка) — свойство корабля в каталоге.
- **Специализация корабля**: две у каждого класса (ТЗ кораблей §9) — в каталоге `specs`.
- **Мастерство класса**: прогрессия игрока по классу кораблей (АР-4(3)).

## 4. Правила авторитетного расчёта характеристик (АР-3)

Итоговые характеристики вычисляет **чистая функция** на сервере: `Stats = Compute(ShipBase, ShipLevel, PilotAttributes, Modules, Talents, ClassMastery, TempEffects)`. Принципы против двойного применения:

1. Каждый бонус имеет **источник** (`source_id`: `talent:N42`, `mastery:fighter:3`, `module:slot2`, `effect:boost`) и применяется ровно один раз; вклад описывается данными, а не накапливается мутацией.
2. Итог **пересчитывается с нуля** из слоёв (снимок состояния → итог), а не «прибавляется» к прошлому итогу. Пересчёт идемпотентен.
3. Порядок слоёв фиксирован: база корабля → уровень → характеристики пилота → таланты → мастерство → модули → временные эффекты; внутри слоя сначала аддитивные, затем множители, затем ограничения (потолки).
4. Клиент получает итог и разбивку по источникам (для подсказок), но не считает сам.
5. Тесты: один и тот же вход даёт один и тот же итог при повторных вызовах; смена порядка применения источников не меняет итог; сброс таланта убирает ровно его вклад.

## 5. Правила PvP-защиты (АР-1)

- Защита — **атрибут региона и состояния**, не станции: `protection = f(регион, состояние пристыковки, флаги боя)`. Сервер решает «можно ли атаковать цель X игроком Y» единственной функцией `CanAttack(attacker, target, now)`; клиент только показывает признак.
- Защищены: главная стартовая станция и стартовый регион (границы в конфигурации мира, проверяются сервером), пристыкованные игроки и интерфейсы станции.
- Обычные станции: NPC-охрана и оборонительные системы, репутационные последствия агрессии; **не** защищают от PvP. Нападение PvE-врагов у станций по-прежнему отключено (R-17), это отдельное правило.
- Сейчас: PvP выключено глобально (`SetAttack` отклоняет игроков), поэтому всё ниже — подготовка к A6, а не включение.

## 6. Влияние на существующие системы

### 6.1. Go-сервер (проверено по коду)

Что есть: `world.Player` хранит корабль (`ShipType`, `Skin`, `Spec`), боевое состояние, груз, косметику; характеристики берутся прямо из паспорта корабля каталога (`ShipSpec`); уровней, талантов, характеристик пилота, мастерства, модулей, предметов нет; `inSafe()` — только для PvE-врагов, продажи и смены корабля; PvP отсутствует (`ErrBadTarget`); стыковки как механики нет (только визуальное событие `dock`); награды идемпотентны через `reward_grants` (`kind` допускает только `credits`).

Что потребуется (новые пакеты в существующем модульном монолите, без микросервисов): `progression` (пилот: XP, уровни, очки), `talents` (граф, версии, проверки, сброс), `stats` (чистая функция расчёта), `mastery` (классы), `ships` расширяется до экземпляров (`player_ships`), `pvp` (`CanAttack`, регионы защиты), позже `items`, `loot`, `crafting`, `expeditions`. `world.Player` получает вычисленный `Stats`; боевая система читает `Stats`, а не паспорт напрямую (изменение за флагом, с проверкой равенства результатов на существующих кораблях). Протокол расширяется аддитивно (версия остаётся 1; старые клиенты игнорируют новые поля).

### 6.2. PostgreSQL

Только расширяющие миграции (ничего не удаляется, значения по умолчанию безопасны). Предлагаемая схема (черновик):

| Таблица | Назначение |
|---|---|
| `pilot_progress` | уровень пилота (1–60), XP, нераспределённые очки характеристик и талантов |
| `pilot_attributes` | значения 6 характеристик |
| `xp_grants` | идемпотентная выдача XP: `UNIQUE (player_id, grant_key)` (как `reward_grants`) |
| `player_ships` | экземпляры кораблей игрока: тип, уровень 1–30, XP, улучшения (`jsonb`), активный корабль |
| `class_mastery` | мастерство по классу кораблей: уровень, XP |
| `talent_graph_versions` | версии графа талантов (снимок `jsonb`, активная версия, откат) — по образцу `world_config_versions` |
| `player_talents` | изученные узлы: `(player_id, node_id)`, версия графа, время |
| `talent_respec_log` | журнал сбросов |

`reward_grants.kind CHECK ('credits')` расширяется до `('credits','xp')` отдельной миграцией (или XP идёт в `xp_grants`; выбор — на этапе реализации, раздел 11).

### 6.3. Godot 4 (Android)

Новые экраны: лист пилота (уровень, 6 характеристик, очки), дерево талантов (панорама и масштаб, **отсечение по видимой области и пулинг узлов** для сотен узлов, связи рисуются батчами), дерево специализации корабля, мастерство класса, уровень корабля в ангаре, полоса XP в HUD, индикатор «защищённая зона» и пристыковки. Бюджет: дерево на 500 узлов не должно держать больше ~100–150 видимых узлов; замер на iQOO 15R обязателен.

### 6.4. Universal Space Studio (админка)

Редактор талантов (граф: узлы, связи, стоимость, требования, эффекты; проверка связности, циклов недостижимых узлов, балансных потолков), версии, предпросмотр, публикация, откат (как «Локации» и «Корабли»); кривые опыта (пилот 1–60, корабль 1–30, мастерство); регионы защиты в «Локациях»; просмотр прогресса игрока и ручная корректировка с журналом. ZIP-патчи для талантов — по аналогии с кораблями (для ChatGPT), позже.

## 7. Обратная совместимость и миграции существующего прогресса

1. **Принцип expand → backfill → switch → (позже) contract.** Сначала добавляются таблицы и столбцы, затем данные заполняются по умолчанию, затем логика переключается за флагом, и только потом (если нужно) убирается старое. Удалений в этой задаче нет.
2. **Существующие игроки:** уровень пилота 1, 0 очков, характеристики по умолчанию; кредиты, квесты, груз, облик, косметика, VIP, аккаунты не затрагиваются. `players.ship_type` → при backfill создаётся первый экземпляр `player_ships` (уровень 1, активный); `ship_type` остаётся и поддерживается как «активный корабль» до отдельного решения.
3. **Старые клиенты (APK):** новые поля протокола игнорируются; без PvP-защиты и талантов они продолжают играть; адрес `ws://IP:8080` не меняется.
4. **Версионирование контента талантов:** снимок графа версионируется; изученные узлы хранят `node_id` и версию; при обновлении графа: добавление узлов — безопасно; удаление или перенос — через миграцию контента (узел помечается устаревшим, очки возвращаются сбросом, журнал). Игроку никогда не «ломается» связность маршрута молча: проверка связности запускается при загрузке и после публикации.
5. **Откат:** каждая функция за флагом (`COSMOC_FEATURE_*`), миграции расширяющие, поэтому откат кода не требует отката схемы; перед любой миграцией на production — резервная копия.
6. **Идемпотентность:** XP, очки, сбросы и покупки улучшений выдаются по ключу события; повтор безопасен.
7. **ИИ-капитаны** подчиняются тем же правилам расчёта и защиты и не создают XP/ресурсы мимо серверных правил.

## 8. Тестирование и нагрузка (план)

- Юнит: `Compute` (детерминизм, порядок слоёв, отсутствие двойного применения), граф талантов (связность, альтернативные маршруты, стоимость, сброс, версии), кривые опыта, `CanAttack` (все комбинации: регион, пристыковка, станция, PvE).
- Интеграция с PostgreSQL: миграции на копии базы production (backfill, повторный запуск), параллельные выдачи XP, одновременные изучения узлов.
- Протокол: новые сообщения, ошибки, права, спам.
- Клиент: тесты раскладки и производительности дерева (счётчики узлов, лимиты, время кадра).
- Нагрузка: 10→30→100 игроков с пересчётом характеристик на событиях (не каждый тик), замер стоимости `Compute`.
- Регрессия: результаты боя существующих кораблей до и после перевода на `Stats` совпадают.

## 10. Неизвестное и риски

- Финальные числа (кривые опыта, стоимость узлов, потолки) не заданы: нужен баланс-проход после RPG-1…RPG-3.
