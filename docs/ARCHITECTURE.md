# Архитектура

## Общая схема

```
Godot-клиент (Android)  --HTTPS/WS-->  Игровой сервер (Go)  -->  PostgreSQL
                                              ^
Админка (React+TS)  ------HTTPS/JSON----------+
```

Сервер авторитетный. Клиент отправляет команды (намерения), сервер валидирует, считает и рассылает состояние.

## Единственный источник истины — сервер

Координаты и движение, характеристики кораблей, здоровье, урон и способности, предметы и ресурсы, валюта и сделки, исследования и производство, результаты idle-заданий, репутация и корпоративное имущество.

## Клиент (`client/`)

Три слоя: сеть (WebSocket, сериализация команд), отображение (сцены, 2.5D-камера, 3D-корабли в SubViewport/3D-слое), ввод (касания, автопилот, способности). Слои общаются сигналами; отображение не ходит в сеть напрямую.

## Сервер (`server/`)

Go, модульная структура:

- `cmd/server` — точка входа, конфиг из переменных окружения, корректное завершение;
- `internal/config`, `internal/log` (структурированные логи), `internal/db` (PostgreSQL, миграции);
- `internal/http` — health, REST для админки и аккаунтов;
- `internal/ws` — сессии, проверка команд, защита от повторного использования токена;
- игровые модули (позже): мир, движение, бой, экономика, idle, фракции, AI.

Серверные события и фоновые задачи: планировщик заданий с идемпотентным завершением (повторная обработка не создаёт дубликатов).

## База данных

PostgreSQL, версионируемые миграции, ограничения целостности. Валютные и предметные операции только в транзакциях. Журнал создания и уничтожения валюты. Порт БД не публикуется наружу.

## Админка (`admin/`)

React + TypeScript. Серверная авторизация, журнал административных действий. Контент: Черновик → Валидация → Предпросмотр → Ручная публикация, с откатом версии (поздние этапы).

## AI-капитаны

Активная система: команды через обычный серверный API. Удалённые системы: событийная симуляция. Дальние организации: агрегированная симуляция. Постоянной языковой модели на капитана нет.

## Idle

Задания хранятся на сервере, результат считается по серверному времени. Удалённые корабли не симулируются в 3D непрерывно.

## Развёртывание

Docker Compose: `server`, `postgres`, `admin`. Подробности в [DEPLOYMENT.md](DEPLOYMENT.md).

## Поставка клиента и контента

Цели: APK не более 100 МБ (желательно), все игровые ресурсы скачиваются в игре.

- **В APK:** движок, код клиента, экран загрузки и подключения, минимальный интерфейс, иконки и шрифты, публичный ключ для проверки манифеста. Тяжёлые 3D-модели, текстуры, звук и музыка в APK не входят.
- **Загрузчик контента (клиент):** при запуске запрашивает манифест (версия контента, список наборов, размеры, SHA-256), докачивает недостающие или изменившиеся наборы в `user://content/`, проверяет хеши, подключает через `ProjectSettings.load_resource_pack`. Нужны индикатор прогресса, докачка после обрыва, повтор при ошибке, предупреждение о размере при мобильной сети.
- **Подпись:** манифест подписывается закрытым ключом (ключ только на сервере); клиент проверяет подпись встроенным публичным ключом (`Crypto.verify`). Подмена файлов в сети или на хостинге не пройдёт.
- **Раздача:** статические файлы наборов отдаёт Caddy (кеширование, Range-запросы); публикация версий идёт через админку по схеме Черновик → Валидация → Предпросмотр → Ручная публикация, с откатом на предыдущую версию.
- **Обновление клиента:** сервер знает минимальную поддерживаемую версию APK. Старый клиент получает от сервера сообщение «нужно обновление». Канал распространения: APK напрямую, позже RuStore (Google Play не используется). Игра сама скачивает новый APK по HTTPS, проверяет SHA-256 и подпись манифеста и запускает установку (нужно разрешение REQUEST_INSTALL_PACKAGES). Правила RuStore на самообновление проверить до публикации в нём.
- **Бюджет размера:** контролируется в CI (размер экспортированного APK, порог 100 МБ). Содержимое наборов не считается в бюджет APK.

## Админка как единая точка настройки (требование владельца)

Universal Space Studio должна позволять настраивать весь игровой функционал и заменять ресурсы: 3D-модели кораблей, текстуры и графику интерфейса, звук, параметры игры, контент (корабли, модули, способности, системы, рецепты, события).

Менеджер ресурсов (поздний этап, после первой работающей игры):
- загрузка файла (glTF/GLB, PNG, WebP, аудио), затем **валидация** (формат, размер, число полигонов, текстуры, бюджет пакета), предпросмотр, ручная публикация, откат на прежнюю версию;
- версионирование каждого ресурса и привязка к сущности («модель корабля X»);
- публикация собирает наборы ресурсов и подписанный манифест; игроки получают обновление через загрузчик контента, без нового APK.

**Открытый технический вопрос** (решить до реализации менеджера ресурсов): как превращать загруженные файлы в наборы для игры. Вариант A: headless-Godot на сервере собирает PCK (импорт, сжатие текстур под Android, проверка): надёжно и экономит трафик, но нужен Godot в контейнере сборки. Вариант B: клиент загружает glTF/PNG напрямую во время работы: проще, без импорта, но без сжатия текстур и медленнее на слабых устройствах. Предварительная рекомендация: A для публикации, B допустим для предпросмотра.
